# PLAN —— 已确认的需求与开发方案

> 执行任何开发任务前，先读本文件相关章节确认需求依据。功能条目与优先级见 `FEATURES.md`；决策理由见 `DECISIONS.md`。

## 一、产品定位

**御膳 · 家庭小厨房** —— 面向家庭场景的移动端应用。一句话：把"今天吃什么"变成可点、可安排、可执行、可采购的闭环。

### 目标用户

| 角色 | 诉求 |
| --- | --- |
| **掌勺人**（如妈妈/爸爸） | 别天天纠结做什么；知道家人想吃什么；按家里有的食材做；别漏买 |
| **家人/吃货**（如孩子、伴侣） | 想吃啥点一下就行；自己的忌口被记住 |
| **朋友**（轻量） | 被分享一份点菜单，勾选想吃的，结果汇总回掌勺人 |

### 核心场景（按重要性）

1. **点菜**：家人点菜 → 掌勺人收到 → 状态流转（待确认→已安排→准备中→已做好）。
2. **决定**：掌勺人不知道做什么 → 按家庭口味/忌口过滤 + 随机配餐 + 常用组合一键加入。
3. **AI 识图入库**：拍一张冰箱照片 → 自动识别有什么食材 → 确认后批量进库存。
4. **AI 识菜分析**：拍一张菜 → 识别是什么菜 → 给出配料与营养（热量/蛋白/脂肪/碳水）。
5. **清库存**：冰箱里有什么 → 看快过期的 → 推荐能用上的菜。
6. **备菜采购**：安排未来 7 天菜单 → 按最终菜单生成不漏项的采购清单（只买缺的）。

> **登录要求**：本产品**必须注册登录后使用**，不做免登录体验（见 `DECISIONS.md` D-008）。

用户同时明确：冰箱页的**主体是冰箱**，采购只占一行（实现第一版把它做成整块预览，被用户当场指出"占据太大位置了，冰箱相关应该才是主题"）。

**2026-10-13 冰箱页降高（D-063，用户选定方案 B）**：用户提"冰箱里有什么和能做点什么现在占据太高了"，并追加"后期还要做 3d 冰箱呢，这块你也要考虑进去"。方案对比稿 `previews/fridge-density.html`（自包含，含现状复刻 + A/B/C 三方案 + 4 种 3D 摆法的高度实测），**用户选定 B**。已落地，约束如下（**这些数字是验收依据，实现后逐区域对照**）：

| 部位 | 改前 | 改后（真机实测） |
| --- | --- | --- |
| 「冰箱里有什么」 | 791px | **378px** |
| 「能做点什么」 | 828px | **266px** |
| 「能做点什么」顶边（首屏 768px） | 969px（不可见） | **566px（可见，露出 212px 的菜）** |

- **四区 → 一行段控**：`常温 2 ｜ 保鲜 空 ｜ 冷藏 10 ｜ 冷冻 空`，点谁看谁；选中那格**全宽两列**（`grid 1fr 1fr`）。改前 2×2 时空格子被同行那格撑到同高（空的「保鲜」「冷冻」各占 136 / 492px 只为说一句"这格里没有东西"）。段控里**空的那颗必须还在**（虚线 + 「空」）且**点得动**。
- **默认展开样数最多的那格**，不是第一格；用户点过之后以用户选择为准（不重算默认值）。
- **菜 → 横滑卡**：卡 `128px`、图 `88px`、徽章压图左上角（`9.5px`）、名字最多两行（`-webkit-line-clamp:2`）。容器 331px 放得下 **2 张整卡 + 第 3 张露 53px**——**露边是唯一的"还能滑"信号**。只摆 5 道，末尾一块虚线「› 还有 N 道能做」，**不是链接**。
- **尺寸（实现约束）**：食材行高 `32 / 37px`，食材图 `26px`，名字 `12.5px / line-height 1.35`（**必须显式给行高**：不给就是浏览器默认 1.6，一行多 3px、两列五行多 15px），区格内边距 `9px 10px`，两列列间距 `10px`；段控行 `30px`；菜品卡 `157px`。
- **状态规则**：选中哪一格、最近录入展没展开，**都要活过路由跳转**（这一页能点进菜谱详情，返回时必须原样）——在 `stores/fridge-view.ts`，**不持久化**（刷新重来）。
- **3D 冰箱（F17-02）位置已定**：分区面板那一格**是 3D 与列表共用的位置**，页内「3D 冰箱 / 列表」两枚切换；3D 块占 **205px**（列表 156px，故接上 3D 只长 49px）。**不采用"3D 常驻叠在列表上面"**（要多 214px，会把做菜块重新顶出首屏）。3D 里的层与分区段控**共用同一份选中状态**。3D 内部如何露出食材留给 M17（F17-02 要求点选食材看名称与保质期，届时要带出列表）。

## 三、技术路线

### 前端

- **React 18 + TypeScript + Vite**，Tailwind CSS，Zustand（状态），React Router。
- **移动端优先**：390px 基准、安全区适配、底部 Tab + 手势。
- **打包**：**Capacitor → Android**（唯一首版目标）；iOS 与 Electron 桌面端暂缓，见 D-002。
- **不做微信小程序**（首版）：定位 App。若后续确认小程序可免费上架，再作为 P2 单独评估（见 `DECISIONS.md` D-010）。
- 说明：Electron **不能**做移动端，故不作为移动端方案（见 `DECISIONS.md` D-002）。

### 后端

- **Node.js + NestJS + Prisma**。
- 数据库统一 **MySQL 8**（本地与服务器同一套 Docker；见 `DECISIONS.md` D-018）。~~开发期 SQLite / 生产 PostgreSQL~~ 已作废。
- **部署形态**：后端与数据库跑 Docker（`docker-compose.yml`），前端不进容器（开发本机 Vite，发布由 Capacitor 打 APK）。
- REST API + JWT 鉴权；图片/视频走对象存储（开发期本地静态目录）。
- 注册登录为强制入口，不做免登录降级路径；云同步为二期能力。

### AI 能力层（用户指定：配置驱动 + pi-agent）

- **harness = pi-agent**：基于 `@earendil-works/pi-agent-core`（Agent 运行时：工具调用、状态管理、**图片附件支持**）+ `@earendil-works/pi-ai`（统一 LLM API、模型发现、provider 配置）。MIT，要求 **Node ≥ 22.19**。
- **模型由用户通过配置文件自行配置**：`provider / baseURL / apiKey / model` 等写进配置文件（如 `config/ai.json` + `.env` 覆盖密钥），**代码零硬编码厂商**；换 provider 只改配置。
- **内置提示词模板库**：冰箱食材识别、菜品识别、营养分析、菜谱生成、配餐建议等多套 prompt，支持用户覆盖。
- **能力边界**：看图识别需要**多模态（vision）模型**，与图片生成网关是两回事；图片生成走 `gpt-image-2`（已实测可用），识图走用户自配的多模态模型。

### 数据

- **菜谱数据模型**：名称、别名、图片、菜系、品类（荤/素/主料）、口味标签、辣度、卡路里（估算标记）、配料与用量、步骤、视频位、来源标记。
- **种子库**：从 `Anduin2017/HowToCook`（Unlicense）导入，产出结构化 JSON。
- **可插拔 Provider**：`RecipeProvider` 接口，实现「内置种子 / 第三方 API / 用户自建」多来源；第三方结果落本地缓存。
- **用户数据**：家庭、成员、点单、菜单、库存、采购清单、口味档案。

### 视觉与素材

- UI 由我方设计，**不照搬参考图**；两套配色主题（暖橙「家庭」/ 清新绿「御膳」）作为可选主题。
- 图标/插画优先 **SVG 自绘**；位图（IP 插画、菜品配图）用 **AI 生成**（`gpt-image-2`，已验证可用）。

## 五、验收标准（每项功能的通用口径）

一项功能算"完成"需同时满足：

1. **可运行**：前端 `pnpm --dir apps/mobile run dev` 可启动、相关页面能打开；后端接口用真实请求验证通过（`pnpm --dir services/api run test:http`）。
2. **符合 PLAN**：与本节描述的行为一致，无擅自扩大范围。
3. **有证据**：记录运行的命令与输出（或截图、本地 URL）到 `NOW.md`。
4. **UI 达标**：视觉符合选定 UI 方案（尺寸/间距/色彩 token）。

## 六、边界与非目标（首版明确不做）

- 不做真实支付、电商下单（参考图中的广告位仅作占位，不做投放系统）。
- 不做社交关系链（关注/私信/评论），内容频道首版只做静态或本地内容。
- 不做视频生成与视频托管（只保留数据字段与播放位）。
- 不做多端实时协同编辑与冲突合并（同步策略二期单独设计）。
- **不自行爬取第三方菜谱站点**（用户 2026-10-12 虽授权爬虫，但实测枚举入口失效且存在反爬，改走**已注册的菜谱 API 多源聚合**；见 `DECISIONS.md` D-019）。数据只用明确许可的来源、API 来源与用户自建，逐条记录来源以便追溯。
- **不做免登录/离线模式**：必须注册登录后使用（D-008）。
- **不自建、不训练视觉模型**：AI 识图一律调用用户配置的多模态模型（D-009）。
