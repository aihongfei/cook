| 来源 | 接口与字段（实际看到） | 能否枚举建库 | 准入与成本 | 合规 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **uapis.cn** | `GET /api/v1/food/recipe?keyword=`（搜索，每次**最多 20 条**，仅 `id/title/cover`）；`GET /api/v1/food/recipe/detail?id=`（详情：`title/cover/description/category/rating/ingredients[]/steps[{step,text,image}]`） | ❌ **仅关键词搜索**，无分类/标签枚举 | **免注册**（访客积分）；搜索 1 积分/次、详情 3 积分/次；4 QPS | ⚠️ 图片托管在 `cp1.douguo.net`，**内容实为豆果美食的转手数据**，文档无来源或许可说明 | 🟡 开发期打通管道可用；**不可作为上架版本数据源** |
| **聚合数据 juhe.cn** id 46 | `https://apis.juhe.cn/cook/query`（GET/POST）：`id/title/tags`（分号分隔，如"家常菜;热菜;红烧;全菜系;1-2人"）/`imtro`/`ingredients`（主料,用量）/`burden`（辅料）/`albums[]`/`steps[{img,step}]`；`totalNum` + `pn`/`rn` 分页（`rn` 最大 30） | ✅ 另有"**分类标签列表**"+"**按标签检索菜谱**"两个子接口，可按标签批量建库 | 需注册 + **实名认证** + **应用场景审核**；**价格需联系客服**（无自助套餐） | 声明"官方直连获取数据，确保数据的合法、合规"；运营方天聚地合（苏州） | ✅ **上架版本的合规首选**，但需先实名与过审 |
| **showapi 万维易源** 1164 | 菜名、分类、详细原料、制作步骤、**小贴士**、图片（具体字段名需 appKey 后在 playground 确认） | 有分类查询；标签枚举未确认 | 需注册 + appKey；免费测试额度 + 付费套餐（额度未公开） | 未说明数据来源 | 🟡 含"小贴士"（正好对应我们模型的 `notes`），需注册后核实字段名 |
| **jumdata 聚美智数** 菜谱查询 / 分类查询 | `POST https://api.jumdata.com/cookbook/list`（`sign = sha256(appId+appSecret+timestamp)`，`productCode=cookbook_query`）；字段 `name/typeV1~V3/tip(小贴士)/largeImg/smallImag/steps[{orderNum,content}]/yl[{ylName,ylUnit}]`；**`type`（分类）必填**，故先调 `cookbook/type` 取分类树 | ✅ 有"分类查询"接口，可按一级/二级分类枚举 | 需注册 + 接口开通 + 计费（`code=200` 即 `charge=true`）；价格未公开 | 未说明数据来源 | 🟡 **实测（2026-10-12）**：接口可用（已成功入库 2 条）；**抽到的菜谱均无图**（文档示例的图片字段也是空串）→ **不满足"图片必须要有"**；步骤很详细但无配图；`yl` 原料部分带用量（`排骨,1.5斤` 可正确解析）、部分只有名称；`tip` 小贴士部分有 |

**字段覆盖对比（相对我们 `Recipe` 模型的必需字段）**：候选源普遍**有**菜名、成品图、配料带用量、步骤（且多为**带配图的步骤**）、分类/标签线索；普遍**没有**菜系、热量、辣度、别名、工具。→ 换源必然要写新的解析器与映射表（外部只给"炒""家常菜"这类标签，`category`/`cuisine`/`tags` 的分法是我们自己定的），这与现有 HowToCook 解析器所做的是同一类工作。

**对既有缺口的正面影响**：这些源自带**成品图与逐步配图**，可直接替代当前"菜谱图片待补"的占位（D-005 的成品图缺口可由数据源解决）；但**卡路里仍无任何源提供**，只能估算或借助 uapis 的「食材营养详情」接口推算（`caloriesEstimated` 标志已有）。

**建议（待用户选定，未定稿）**：开发期用 **uapis**（免注册、零成本、已验证可用）把"外部源 → 导入 → 落库 → 列表/详情/筛选"的管道打通，让 UI 尽快有真实数据；同时并行注册**聚合数据**走实名与场景审核（审核需要时间），上架前切到合规源。切换成本低，因为 `RecipeProvider` 适配层（F1-03）本就是为换源设计的。**风险提示**：uapis 数据为第三方版权内容的转手分发，仅可作开发期使用，不宜随应用上架分发。

### 爬虫可行性实测（2026-10-12，用户已授权爬虫）

用户明确"可以做爬虫"后，我方先做可行性验证再决定是否投入，**实测结论是不自建爬虫**（已落档 `DECISIONS.md` D-019）：

| 目标站 | robots.txt | 枚举入口 | 详情页可达性 | 结论 |
| --- | --- | --- | --- | --- |
| **豆果 douguo.com** | ✅ 有（`Crawl-delay: 1`，仅禁 `/app/`、`/printcook/*` 等；提供 sitemap） | ⚠️ sitemap 索引含 **375 个 dish 子图 × 5 万条 ≈ 1875 万** URL，但抽样 `/dish/{id}` | ❌ curl 与**真实浏览器均 404**（sitemap 内链接已失效）；`/cook/*`、`/caipu/*` 变体则连接超时 | ❌ 枚举入口不可用 |
| 下厨房 xiachufang.com | 无（404） | 未验证（探测的分类路径 404） | 未验证 | ❌ 不投入 |
| 美食杰 meishij.net | 无（404） | 探测路径 404 | 未验证 | ❌ 不投入 |
| 香哈 xiangha.com | — | — | 首页连接失败（HTTP 000） | ❌ 不可达 |

**关键事实**：豆果同一站点的 sitemap 可以正常下载，而菜谱详情路径先 404、随后直接连接超时——这是**按路径的反爬**，不是网络问题。要稳定抓取需引入浏览器渲染 + 代理池 + IP 轮换，属独立工程线；且站点改版会让解析器持续失效，版权风险也最高。

**反例（说明 API 才是更优解）**：同期 `uapis.cn` 连续三次调用均正常返回结构化 JSON（成品图 + 配料带用量 + 步骤含配图）——API 本质就是"别人已经维护好的爬虫"，且用户已完成多平台注册。

### 极速数据深度实测（2026-10-12 当晚，用户开通接口权限后，用真实 key 跑通）

上面那张表的判断已被真实调用验证，并且拿到了文档里看不到的若干约束（**都已实测，非文档推断**）：

| 实测项 | 结果 |
| --- | --- |
| 鉴权状态 | 权限开通前 `{"status":"103","msg":"APPKEY无请求此数据权限"}`；**在后台开通「菜谱」接口后 `status=0`**。→ 103 是"密钥有效但接口没开通"，只能去后台申请，不是代码问题 |
| 分类树 `class` | `result` 是数组，**14 个顶级分类、子类合计 900+**（菜品 88、菜系 106、功效 176…）。注意**多数顶级分类不是菜品**（功效/人群/疾病/体质/场景/口味/加工工艺/厨房用具），真正的菜品分类在「菜品(301)」下 |
| 枚举 `byclass` | **一次返回含 `material`/`process` 的完整菜谱**（不需逐条再调详情）；`result` 是**对象** `{ total, num, list }` 而非数组；**`num` 硬上限 20**（传 50/100 都只回 20）；**只认叶子分类**（传顶级 id → `205 没有信息`）；`start` 翻页有效（start=0 与 start=5 返回的 id 不重叠） |
| 原料字段 | `material[] = {mname, type, amount}`，**`type` 是数字**：1 主料、0 辅料，且**主料排在数组末尾** |
| 图片分辨率 | 实测 **230×230 px / 16KB JPEG**（此前文档示例图只有 178×134，实际略好） |
| 图片协议 | `pic` 给的是 `http://`，但**同域名 https 请求同样返回 200**（实测 230×230 / 16KB）→ 可强制 https，规避 APK 内混合内容拦截 |
| 数据量 | `total`：家常菜 **12710**、热菜 2681、川菜 456、搜索"番茄炒蛋" 25 |
| 调用成本 | 建库实测 **32 次调用 / 52 秒 → 入库 640 条（去重后 600 道）**；按 20 条/页，**拉满家常菜约 636 次调用** |
| 图片链接会过期 | 文档原文："菜谱图片（链接会过期，请您尽快保存图片）" → **转存自有存储是必做项**（`RISKS.md` R-05 第 1 条） |

**结论**：极速数据是四个候选里**唯一同时满足"有图 + 量大 + 能枚举 + 便宜"**的源，已定为主力源（`DECISIONS.md` D-019 第 7 条）。它的短板是：① 图片分辨率只有 230×230（详情页大图位会显糊，`RISKS.md` R-02 残余项）；② 图片链接会过期，必须转存；③ 数据版权归属与商用许可仍未核实。

**参考对照（如何选源）**：`uapis` 有图但只能关键词搜索，适合做补充与开发期兜底；**极速数据的 `byclass` 枚举能力才是把库填到几千道的正解**。

## 六、AI 能力选型调研（2026-10-11 追加）

需求：拍照识别冰箱食材并自动入库存；拍照识别菜品并给出配料、营养。

### 实测结论：用户现有网关不支持识图

| 探测 | 结果 |
| --- | --- |
| `GET /v1/models` | 仅 4 个模型：`gpt-image-2`、`gpt-image-2.5-flare`、`gpt-image-2.5-sunburst`、`z-image`，`supported_endpoint_types` 全为 `["image-generation","openai"]` |
| `POST /v1/chat/completions` | 不返回文本，而是返回一张 base64 图片（被代理到出图模型） |

→ **该网关只能生成图片，不能看图理解**。识图必须另配多模态模型。

### 可选多模态（vision）provider（均为"用户自配"候选）

| 方向 | 代表模型 | 备注 |
| --- | --- | --- |
| 国内云 API | 通义千问 VL（qwen-vl / qwen3-vl）、智谱 GLM-4V、豆包 vision、混元 vision、文心 ERNIE-VL | 中文场景好、单价低、有免费额度；需实名 |
| 海外 API | OpenAI gpt-4o/gpt-5 vision、Google Gemini、Claude | 识图强；网络与合规成本高 |
| 本地部署 | Qwen-VL 等开源权重自部署 | 无 API 成本、数据不出内网；但需 GPU 与运维，首版不建议 |

### 设计结论（用户已指定）

- **不锁定任何厂商**：provider/baseURL/model 全部走**配置文件**，用户自己填。
- 我方交付：**内置提示词模板库** + **调用 harness**（pi-agent）。
- 提示词需覆盖：冰箱食材识别（输出结构化食材+数量+置信度）、菜品识别、营养与配料分析、菜谱草稿生成、配餐建议。

### harness 选型：pi-agent（用户指定，已核实）

| 包 | 最新版本 | 作用 | 授权 |
| --- | --- | --- | --- |
| `@earendil-works/pi-agent-core` | 1.1.0 | Agent 运行时：工具调用、状态管理、**图片附件（attachment）支持** | MIT |
| `@earendil-works/pi-ai` | 1.1.0 | 统一 LLM API + 自动模型发现 + provider 配置 | MIT |

## 七、国内推送通道准入门槛调研（2026-10-12，为 M10 通知做的前置核查）

**背景**：用户家里两部手机是 **vivo、荣耀**，本人是**个人开发者、不上架任何应用商店、直接发 APK**。要回答的是"App 完全关闭时能不能收到提醒"。

结论先行：**在这个前提下，vivo 机型做不到"App 关闭也收到"，荣耀存在空间但资质口径冲突；极光/个推绕不过厂商门槛；FCM 在无 GMS 国产 ROM 上不可用。**

### 7.1 逐通道对照

| 通道 | 资质要求 | 必须上架商店 | 费用 | 可信度 |
| --- | --- | --- | --- | --- |
| **荣耀 Push** | 官方允许个人实名认证；但官方权益表写个人"应用管理**仅限 web 应用**"（暗示个人不能给安卓应用开推送），而极光文档直写荣耀通道"需要**企业**开发者账号"——**口径冲突** | **否**（开通只要：注册→管理中心→填包名+SHA256→签协议） | 免费；但资讯营销类默认 **2 条/设备/天且静默**，要另申请分类权益 | 上架=否、免费 已核实；个人资质 **需实测确认** |
| **vivo Push** | 接入流程指向《**企业**开发者注册》；个人上架通道 2026-09 起"逐步开放**受邀**开发者体验" | **是，硬性**——"应用必须上架才具备线上推送能力"，未上架只有【受限】权限（只能发测试消息，1000 条/天） | 免费，但额度受限；**2025-02-17 起非 vivo 官方渠道安装的应用默认关闭接收"运营消息"** | 已核实 |
| **极光 JPush** | 账号本身免费可建应用；**厂商通道按各厂商规则**（官方表格：vivo/OPPO/小米/荣耀＝企业账号） | 取决厂商通道 | 有永久免费版（广播 10 次/天等）；付费价未公开 | 厂商资质 已核实 |
| **个推 Getui** | 免费注册可用；厂商通道各自开通 | 取决厂商通道（其小米章节明说未上架无法启用） | 免费版仅消息下行；VIP **3000 元/月起** | 计费 已核实 |
| **自建长连接 + 前台服务** | 无 | 不涉及 | 仅自有服务器 | 见 7.3 |

**关键一点**：不存在"聚合服务把厂商通道打包后自动豁免上架/资质"——极光官方上架说明表自己写死了"部分厂商要求必须上架应用市场才可以使用推送服务"。

### 7.2 FCM 在国产 ROM 上不可用

- Firebase 官方原文："FCM 客户端需要在搭载 Android 6.0+ 且**安装了 Google Play 商店应用**的设备上运行"；
- 腾讯云移动推送官方 FAQ 原话："**Google 服务和可以正常访问 Google 网络是使用 FCM 的必要条件**"；
- 所以"设备装了 Google 框架就能收"不成立（还要能连通 Google 服务端网络），且国产 ROM 的后台策略仍会限制。

### 7.3 绕过厂商通道的路径与真实边界（都有出处）

- Android 12+ **后台不能随意启动前台服务**（`ForegroundServiceStartNotAllowedException`）；Android 14+ 必须声明 FGS 类型；
- Android 15 的 `dataSync` 前台服务 **24 小时内共享最多 6 小时**，超时被系统强制停；且不允许从 `BOOT_COMPLETED` 启动；
- Doze/App Standby 闲置时**暂停应用的网络访问**，长连接在息屏久置后必然断续；
- 腾讯云官方 FAQ："目前**第三方推送都无法保证关闭应用后仍可收到推送消息**，该问题为手机定制 ROM 对移动推送 Service 的限制"——QQ/微信是厂商级白名单才能常驻。

### 7.4 对本项目的落地建议

1. **荣耀机型**：值得实测（个人账号提交一次申请，免费，1–2 工作日见分晓）。若能开通，后端只需一个 HTTPS 调用（`https://push-api.cloud.honor.com/api/v1/{APPID}/sendMessage`），是本方案最划算的部分。
2. **vivo 机型**：官方门槛明确，个人 + 不上架拿不到正式推送权限。**不要在这里投入集成成本。**
3. **通用兜底（不依赖任何厂商）**：本机可判定的事件（计时结束、快过期到点）走 **Capacitor Local Notifications**（无门槛，Android 13+ 申请通知权限）；远端事件（别人点了菜）走**打开 App 时同步 + 应用内红点**。这正是 M10 交付一 + 交付二的分界。
4. **Capacitor 集成现状**：`@capacitor/push-notifications` **只支持 FCM/APNs**（官方文档原话 Android 端 "uses Firebase Cloud Messaging SDK"），走厂商通道必须引第三方 SDK 或自写原生桥接；JPush 有官方 Cordova 插件（可经 Capacitor 兼容层用），个推只有低维护度社区插件。

### 7.5 仍未收口的三件事（**待核实**）

- **荣耀个人资质**：官方文档与极光文档冲突 → 建议以一次真机/真账号实测收口；
- 聚合服务的付费价格（两家都未公开列示）；
- 各 ROM 具体的后台清理行为（需真机实测，不能只看文档）。

## 八、米家接入调研（2026-10-16，用户问「能不能把米家里的设备显示在我的软件里」）

**背景**：用户问能否接入米家、把米家设备显示进「御膳」、难度如何。本项目形态：自建后端（公网服务器）+ Capacitor 安卓壳（WebView）；家庭自用、不上架商店、个人开发者。

结论先行：**能做，但没有"官方给自建 App"的直连通道**；唯一官方的干净路径是**绕经 Home Assistant**（用户家里自建），社区逆向方案有失效与账号风险、且与本项目「后端在公网」的架构不合。**代码工作量不大，门槛在前置条件与一条许可红线。**

### 8.1 三条路径对照

| 路径 | 做法 | 前置条件 | 判定 |
| --- | --- | --- | --- |
| **A. 自建 Home Assistant + 官方米家集成，App 读 HA 接口** | 家里一台机器跑 HA，装官方集成（`XiaoMi/ha_xiaomi_home`）；本项目读 HA 自己的 REST API（`GET /api/states`、`POST /api/services/*`，长期访问令牌鉴权） | 家里常驻一台机器（NAS / 树莓派 / 旧电脑）；小米账号 OAuth 授权；App 与 HA 网络可达 | **官方支持、较稳**；代价是用户侧运维 + 网络可达性（在家直连；在外经后端中转，需内网穿透） |
| **B. 社区逆向库** | python-miio（本地）/ micloud（云端 token）/ hass-xiaomi-miot 直连设备或小米云 | 抓设备 token 或交账号密码；本地模式要求查询方与设备同局域网 | 依赖小米私有接口，**随时可能失效**；账号有风险；**与公网后端架构不合** |
| **C. 官方 iot.mi.com** | — | — | **不通**：公开可见流程均为企业/硬件产品方向（"注册企业组""成为企业开发者"）；未发现个人开发者"读米家设备"的通道 |

### 8.2 许可红线（关键：8.1 的 A 只能"绕"不能"搬"）

`XiaoMi/ha_xiaomi_home` 是小米官方发布、仍在维护的集成（约 22.2k star；2024-09 建仓，最近提交 2026-09），但它的许可证是小米自定义的**专有许可证**（GitHub 标记 NOASSERTION / Other），原文：

> "本许可证未授权您将授权作品用于任何其他用途，包括但不限于**开发应用程序（APP）**、Web 服务以及其他形式的软件等。"

其 LegalNotice 亦把"**在非 Home Assistant 平台上使用小米云接口**"列为侵权。

**结论**：**不能**把该集成的代码/接口搬进本项目 App；**可以**让集成跑在用户自己的 HA 里，本项目只读 HA 公开发布的 REST API（HA 本体是开源项目，其 REST API 有官方文档）。

### 8.3 设备范围与边界（决定"能看到什么"）

- 官方集成**不支持**：蓝牙设备、红外设备、虚拟设备；
- **本地控制**依赖**小米中枢网关**（仅中国大陆）；局域网直连只能控"同一局域网的 IP 设备"，**控不了 BLE Mesh / ZigBee**；
- **云端控制**走 MIoT Cloud（MQTT 订阅 + HTTP 下发），不需网关、但依赖小米云；
- 登录用小米账号 OAuth 2.0（文档未要求自备开发者 app_id/app_key）。

### 8.4 社区库当前状态（2026-10-16 实测查证）

- `python-miio`：4.3k star；PyPI 最新 0.5.12（2024-03）；README 称正在大重构；
- `micloud`：PyPI 最后发布 0.6（**2022-12**，陈旧）；
- `hass-xiaomi-miot`（al-one）：6.2k star，仍活跃；支持 WiFi/BLE/ZigBee；**轮询制**（部分传感器事件不实时）；
- Node/JS 的 `miio` 包：**最后发布 2018-02，已死**——JS 侧没有可用的现成库。

### 8.5 难度评估（对本项目）

- **工作量**：读状态 ≈ 一个 JSON 接口 + 一个列表页；若含控制，经 HA 的 `POST /api/services/*` 同样是薄封装。**中等偏小。**
- **真门槛**（都不是代码）：
  1. 家里要有一台**常驻在线**的机器跑 HA（一次性配置 + 长期供电联网）；
  2. **网络可达性**：在家直连 HA 最简单；在外网要么暴露 HA（不建议）、要么经本项目后端中转（家里 HA 需可被访问，通常要内网穿透）；
  3. **设备类型**：没有小米中枢网关的家庭，蓝牙/红外类设备在这条路上看不到（见 8.3）。
- **红线**：不得把官方集成挪进自建 App（8.2）。

### 8.6 本次未收口（待核实）

- 小米中枢网关对 Matter 桥接的支持与能否复用（Matter 控制器要在 App 侧实现，工程量与 A 路径不在一个量级）；
- iot.mi.com 是否存在未公开的个人通道（本次只核到公开企业流程）；
- 若走 A 路径，HA 部署成本（机器来源、内网穿透方案）取决于用户家里条件，落地前需实测。
